# WO-214 — Retry at most three times, withheld while the switch is off — and unpublish()

- Branch: wo/WO-214-publish-retry-unpublish
- Estimate: ≤1 day

## Goal
Ship the retry policy — retryable reasons only, at most three, backed off, withheld while publishing is off — and `unpublish()`, available for as long as the page is published.

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/attempt/retry.ts` | NEW | The policy as one pure decision plus its scheduler. A `failed` page schedules a retry only while `reason ∈ RETRYABLE` and `attempt_no < 3`; otherwise `failed → needs_attention` is taken in the same invocation, so no page rests in `failed` with neither a retry due nor that move made. While the switch is off the retry is **withheld and the page held in `failed`** — the one legitimate rest — and becomes due again on resume. Backoff from BP-005's `PUBLISH_RETRY_BACKOFF_MIN` (`[5, 30, 180]`), never a literal here. |
| `src/lib/publish/attempt/unpublish.ts` | NEW | `unpublish()`, **returning BP-045's `UnpublishResult` — the four-arm closed union, not the boolean `{ ok: true; removedFromDestination: boolean }` this work order carried before ADR-081.** Calls `adapterFor(kind).unpublish(pub, cfg)`, sets `publications.unpublished_at`, takes `published → unpublished` through `transition()`, and **returns the adapter's outcome unchanged** — it neither re-derives the arm nor collapses the three into a boolean. Available for as long as the page is `published`. **No publication row is deleted** (ADR-080 decision 2). One edge, three outcomes: hosted returns `removed` and the address answers 410 (BP-047); WordPress returns `returned_to_draft` or `named_for_removal` according to `publications.made_live_by_us` (BP-048, WO-239). **This function does not read `made_live_by_us` itself** — the adapter is handed the `Publication` and reads it (BP-045's `unpublish` note: "Which arm is taken is read from `publications.made_live_by_us`, never from a re-read of the destination"), so the discriminator is consulted in exactly one place. |
| `tests/publish/attempt/retry.test.ts` | NEW | Each of the nine `FailureReason` members is retried or not according to `RETRYABLE`; the third failure moves to `needs_attention`; no page is left in `failed` with neither a scheduled retry nor that move; with the switch off a due retry is withheld and the page stays in `failed`, and becomes due again on resume. |
| `tests/publish/attempt/unpublish.test.ts` | NEW | `unpublish` is offered for every `published` page and at any time; it sets `unpublished_at` and deletes no row; a subsequent publish attempt against the unpublished page creates no post; on a hosted destination the outcome is `removed`. **Pass-through, asserted three ways:** a stub adapter returning each of `removed`, `returned_to_draft` and `named_for_removal` produces exactly that outcome from `unpublish()`, and `published → unpublished` and `unpublished_at` are identical in all three — the state change does not vary by arm. The `returned_to_draft` row is the one that would silently disappear if the union were collapsed back to a boolean, and it uses a stub adapter precisely because no production adapter returns it today (ADR-081). |

## Interfaces

**Consumes**

- `FailureReason`, `RETRYABLE`, `publish()` — `src/lib/publish/attempt/index.ts` (WO-213).
- `UnpublishResult`, `Publication` — `src/lib/publish/types.ts` (WO-206).
- `transition()` — WO-209.
- `isPublishingOn(siteId)` — WO-210.
- `adapterFor(kind)` — BP-058, WO-225.
- `PUBLISH_RETRY_BACKOFF_MIN` — BP-005, `src/lib/config/constants.ts`, asserted in `tests/pins.test.ts`.

**Exposes** — copied exactly from BP-045's `## Public interface`:

```ts
/** ADR-081. Three outcomes, never a boolean: a boolean cannot separate "the
 *  post ReachKit made live is a draft again" from "the post ReachKit never made
 *  live was named and not touched", and those are two different promises to the
 *  customer about their own site. */
export type UnpublishResult =
  | { ok: true;  outcome: 'removed' }             // hosted — REQ-056 c15, 410 at BP-047
  | { ok: true;  outcome: 'returned_to_draft' }   // WordPress, made live by us — REQ-079 c4
  | { ok: true;  outcome: 'named_for_removal' }   // WordPress, never made live — REQ-056 c16
  | { ok: false; reason: FailureReason }

export function unpublish(a: { draftId: string; by: Actor }): Promise<UnpublishResult>
```

`UnpublishResult` is declared in `src/lib/publish/types.ts` (WO-206) and is
consumed here, not re-declared. BP-045's `unpublish` returned
`{ ok: true; removedFromDestination: boolean }` when this work order was cut;
ADR-081 replaced it, because a boolean cannot carry three outcomes and the two
WordPress arms are two different promises about a site ReachKit does not own.

## Steps
1. Create `attempt/retry.ts` with the decision as a pure function of `(reason, attemptNo, switchOn)` and a thin scheduler over it, so every limb is testable without a clock.
2. Read `PUBLISH_RETRY_BACKOFF_MIN` (`[5, 30, 180]`) from BP-005's `src/lib/config/constants.ts`. Do not add it here and do not inline the numbers: `src/lib/config/**` is BP-005's under structure.md, and a number in two files is wrong (rule 5). If the pin is absent when the implementer starts, they stop and log `failed — next: wait on BP-005's pins work order`.
3. Create `attempt/unpublish.ts`. Set `unpublished_at`; delete nothing. Return the adapter's `UnpublishResult` unchanged: no `switch` in this file maps an outcome to a boolean, to a message, or to a different state edge. Read ADR-081's warning block first — `returned_to_draft` has no members in production today and a `default:` arm that folded it into `named_for_removal` would break nothing here and no test but the three-arm pass-through above.
4. Write the "no page rests in failed without a retry due or the move made" property test first and watch it fail against an implementation that only retries (constitution §8).

## Out of scope
- What the WordPress adapter does inside the customer's site on unpublish — **BP-048, WO-239**, which owns both arms. BP-048's `blocked-by: [REQ-079]` was discharged by ADR-081 on 2026-08-31 and the write path is cut. This work order calls the adapter and does nothing with which arm it took beyond returning it.
- Reading `publications.made_live_by_us`. The adapter reads it from the `Publication` it is handed (BP-045); this function does not branch on it.
- Republishing an unpublished page or restoring a skipped one — REQ-056 criteria 3 and 5 forbid it and the table has no such edge.
- The job schedule that invokes the retry — BP-003's `publish/execute`.

## Rollback
Delete the four files. `publish()` stands without a retry policy, which is a degraded but not incorrect state: a failed page simply rests in `failed`, which is why the property test above exists.
