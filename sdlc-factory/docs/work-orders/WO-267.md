# WO-267 — The Supabase substrate — project config, baseline schema, RLS default-deny, and the two clients

- Branch: wo/WO-267-supabase-substrate
- Estimate: ≤1 day

## Goal
Stand up BP-002 as one capability, from its config to its clients: the local
Supabase project, the baseline migration of the eight tables no other node
owns, the row-level policies that make every table default-deny and a
tombstoned account unreachable through `db()`, and the two clients — the only
two ways any module reaches Postgres — with the generated `Database` type.

## Why one order (rule 2.6)
WO-008, WO-009, WO-010 and WO-011 cut BP-002's one capability horizontally by
file: WO-009 left its tables "unreadable until WO-010 lands", WO-010's rollback
read "do not revert WO-009 without also reverting this one", and WO-011's types
are generated from the schema WO-009 and WO-010 applied. None of the four could
state its stop condition without citing the others, which is the merge test.
Criteria and file plans below are carried verbatim, none dropped.

## Provenance of this file plan
**This repository holds no `supabase/` and no `src/`.** Every path is NEW,
anchored to `structure.md`'s row for `supabase/**` · `src/lib/db/**` and to
BP-002's `code:` globs.

## Steps
1. `supabase init`; edit `config.toml` for magic-link auth; write `topics.ts`
   from `structure.md` rule 3 and 3a and the naming test with its four fixture
   names — watch the unassigned case fail before the check exists.
2. Write the baseline migration table by table in `BUILD.md` §10's order,
   skipping `fetches`; enable RLS on all eight with no policy; add the indexes
   BP-002's NFR budget requires; apply locally.
3. Write the policy migration: the `deleted_at` column, one policy per table per
   operation naming the owning user, the `deleted_at is null` condition on every
   request-scoped policy.
4. Generate `types.generated.ts` with `npm run db:types` (the script WO-001
   declares); write the two clients and the client-bundle guard.
5. Write the four test files. Watch each fail first: add one cascade, drop one
   table's policy, remove the condition from one policy, add a column without
   regenerating types — then restore each.

  together. `email_suppressions` — BP-029's `*_suppressions*.sql`.

  Supabase project, key rotation, and any remote apply.

## Rollback
Delete `src/lib/db/**`, `tests/db/**`, the two migration files and the
`supabase/` directory, and reset the local database. Nothing has been applied to
a hosted project. Reverting the policy migration alone returns every table to
"RLS on, no policy", which is unreadable rather than open — the safe direction;
the baseline is never reverted without it.

### Deviation 1 — `dbAdmin()` build-time guard: lexical checker instead of `import 'server-only'`

**The reasoning, verified independently, not taken on the implementer's word:**
- `node -e "require.resolve('server-only')"` fails in this repo (`MODULE_NOT_FOUND`) — the package is genuinely unresolvable here.
- `package.json` carries no `server-only` entry and is genuinely outside WO-267's ten-file plan.
- The lexical alternative is a reasonable rule-4.2 deviation, stated once, in one place (the module header and the test file header) — judged **acceptable** on those grounds.

**"The runtime guard is asserted separately so removing either fails a case" — judged NOT MET, for the runtime half specifically.** I removed `dbAdmin()`'s own `typeof window !== "undefined"` check from `src/lib/db/index.ts` (restoring after) and re-ran `tests/db/clients.test.ts`: **all 17 tests still passed, including both runtime-half tests** ("dbAdmin() throws when evaluated where window exists" and "removing the runtime guard alone would not be caught by the build-time check — the two are independent"). Root cause, confirmed with a standalone probe script (`tsx`, `globalThis.window = {}`, direct import of the mutated module): the throw the tests observe comes from `src/lib/config/env.ts`'s own `SERVER_ONLY_KEYS` guard on `SUPABASE_SERVICE_ROLE` (BP-005/WO-005, `"SUPABASE_SERVICE_ROLE" is server-only and cannot be read from a client bundle`) — a different module's guard, reached because `dbAdmin()` reads `env.SUPABASE_SERVICE_ROLE` inside the same function body, and whose message happens to contain the substring `"server-only"`, which is exactly what the second runtime-half test's `toThrow(/server-only/)` matches on. In the **unmutated** code the `typeof window` check does fire first and does own the throw (confirmed by inspection — it is the function's first statement) — the finding is that the test suite has no case that would catch its *removal*, which is precisely constitution §8's "a test that survives deletion of its feature is vacuous," applied here to one half of one criterion rather than the whole row. The security property in production is not broken — `env.ts`'s independent guard genuinely still stops `dbAdmin()` reaching a browser bundle — but the WO's own sentence, read literally, is false for the runtime half as shipped.

**This is a FAIL for row 16's runtime half** and is the one defect this report sends back. Fix: make the runtime-half tests isolate `dbAdmin()`'s own guard specifically — e.g. stub/bypass `env.ts`'s `SUPABASE_SERVICE_ROLE` guard for that one test (so only `dbAdmin()`'s own check can produce the throw), or assert the specific error message `dbAdmin()` itself throws (`"dbAdmin() is server-only and cannot be evaluated in a client bundle"`) rather than a shared substring both guards happen to contain.
