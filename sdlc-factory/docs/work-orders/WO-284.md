# WO-284 — Bind the boot environment to the deployment — SUPABASE_SERVICE_ROLE_KEY end to end, NANO_API_KEY optional, DATABASE_URL out of Env

- Branch: wo/WO-284-boot-environment
- Estimate: ≤1 day (one schema, one reader, six fixtures, one example file)

## Goal
Move `env.ts`'s boot schema and every reader and fixture of it onto BP-005
decision 6's three bindings in one commit, so a deployment on the Vercel
project `reachkit` boots on the names that project holds and an environment
carrying the retired names fails loudly instead of half-configuring.

> **Read `blueprints/BP-005.md` decision 6 (6a, 6b, 6c) before writing a
> line.** It holds the derivation and the reversal cost of each of the three
> bindings, and the standing fact about write-only secrets they follow from.
> None of that is restated here (rule 2.4).

## Provenance of this file plan
Every path below exists; every one is MODIFY. **Type fan-out (rule 1b):** the
two type-shape edits — schema key renamed, `DATABASE_URL` row deleted — were
applied alone on a scratch copy of `src/`, `tests/` and `tsconfig.json` (whose
`include` covers `tests/**`) and `npm run typecheck` run against it. Baseline
exit 0; after the edit, exactly one error — `src/lib/db/index.ts(58,64): error
TS2551: Property 'SUPABASE_SERVICE_ROLE' does not exist on type
'Readonly<{ … }>'. Did you mean 'SUPABASE_SERVICE_ROLE_KEY'?` — so that file is
the only type-change row. What did *not* error is the finding: every other
consumer names the binding as a **string literal** in a `process.env` fixture
where no compiler can see it, so the six test files and `.env.example` are grep
rows, not type rows. Separately: `tests/config/env.test.ts` falls under no
blueprint's `code:` globs (BP-005 globs `src/lib/config/**` and
`tests/pins.test.ts` only) — flagged to the architect, not repaired here.

## Interfaces
Exposes (verbatim from BP-005 `## Public interface`):
```
//   SUPABASE_SERVICE_ROLE_KEY — the platform's name for §15's
//   `SUPABASE_SERVICE_ROLE`, and after decision 6a this file's only name for
//   it. Same secret, same value; §15's name is retired.
//   NANO_API_KEY — the one optional member. Absent, it resolves to
//   `ANTHROPIC_API_KEY`. To every reader the member is still a required
//   `string`, so **BP-009's interface is untouched**
//   DATABASE_URL — **not a member of `Env`.** No module under `src/` reads it;
//   it is the migration and test tooling's binding (decision 6c).
```
Consumes: nothing new. `env.ts` still imports only `zod` (BP-005 "imports
nothing").

## Steps

   case against the unchanged `env.ts` and record them red.
2. Edit `env.ts`.
3. Edit `src/lib/db/index.ts` (the TS2551 row) and run `npm run typecheck` to 0.
4. Move `.env.example` and `tests/app/env-example.test.ts`'s list **together**.
5. Move the five remaining fixtures.
6. Mutation probes: restore the `SUPABASE_SERVICE_ROLE` key alone and watch the
   retired-name case fail; delete the `ANTHROPIC_API_KEY` resolution alone and
   watch the absent-`NANO_API_KEY` case fail; restore `DATABASE_URL` to the
   schema alone and watch the boots-without-it case fail.

  `llm()`'s `tier: 'nano' | 'haiku'` argument, its closed call-site union and
  the model id each tier binds to are unchanged." No call site is edited, no
  tier is added, removed or reselected. WO-026 was re-read against 6b and
  needs no change: it names `ANTHROPIC_API_KEY` and `NANO_API_KEY` as bindings
  read from `env`, and both remain exactly that.
- Any value. Nothing is set, read back or asserted — the deployment's
  variables are write-only (decision 6's standing fact), and the one claim
  about names being present on the project is BP-005's `rests-on` row, not
  this order's to raise a second time (rule 2.4). Renaming anything on the
  Vercel project is likewise out: the corpus moves, the platform does not.
- The migration and test tooling's own `DATABASE_URL` handling. Those callers
  already read it from the process environment; this order removes the boot
  schema's row and adds no tooling code.
- `vitest.config.ts` — WO-283's file. This order edits fixtures inside three
  files that project lists; it changes no file's project membership.
- Every other binding in the schema. Thirteen names are untouched.

## Rollback
`git revert` the single commit: the schema row, `SERVER_ONLY_KEYS`, the one
`dbAdmin()` read, six fixtures and `.env.example` all return together. No
migration, no data, no customer-visible string moves either way. Decision 6a's
own note applies — "Reversing to the *alias* shape instead is one mapping line
here and no downstream edit."
