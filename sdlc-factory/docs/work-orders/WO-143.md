# WO-143 — deleteAccount — signed out, subscription ended, tombstone stamped, and one mail about what is still live

- Branch: wo/WO-143-delete-account
- Estimate: ≤1 day

## Goal
Run the deletion arm in the fixed order — take the pages down, end the
subscription at once, stamp the tombstone and the promised purge date, sign the
customer out — and write once to the address being deleted about any pages a
destination would not let go of.

## File plan
> **Every path below is NEW except `confirm.ts`.** No `src/` exists; `confirm.ts`
> is created by WO-142 and modified here, which is why the two are sequential.
> Anchored to `registry/structure.md` and BP-063's `code:` glob
> `src/lib/account/lifecycle/**`. Provisional against a repo with no code.
>
> **Read ADR-051 before writing this file.** `deleteAccount` "sets
> `users.deleted_at = now()` and `users.purge_due_at = now() + ERASURE_DAYS`. It
> issues no `DELETE` of any kind." Finishing the delete path is the mistake the
> ADR exists to prevent.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/account/lifecycle/delete-account.ts` | NEW | Exports `DeleteAccountResult` verbatim and the deletion sequence, in BP-063's fixed order, each step a precondition of the next: (1) run WO-142's take-down loop and collect `stillLive`; (2) end the subscription **at once** through BP-060 — cancel immediately and set `paid_through = now()`, so `hasActiveAccess` is false at once, the hosted 30-day retention window never begins and **neither hosting notice is sent**; (3) set `sites.hosted_serving_ends_at = now()` so BP-060's `hostedServingState` answers `serve: false` — there is no second switch (decision 5); (4) stamp `users.deleted_at = now()` and `users.purge_due_at = now() + ERASURE_DAYS`, the date **stored**, not computed (decision 4); (5) end every session for the user; (6) where `stillLive` is non-empty, send one `account` mail to the address being deleted, naming the pages left live and what the customer must do to remove them — composed through `dbAdmin()`, because the tombstone has already hidden the rows from `db()` (ADR-051 point 3). | `src/lib/account/lifecycle/confirm.ts` | MODIFY | Add the `delete_account` arm to `confirmDangerAction`'s existing switch, behind the same ticket guard. No other line changes. |

## Interfaces
Exposes (verbatim from BP-063's `## Public interface`):
```ts
export interface DeleteAccountResult {
  signedOut: true
  subscriptionEndedAt: Date
  stillLive: UnpublishAllResult['stillLive']   // c6 — named in one `account` mail to the deleted address
  purgeDueAt: Date                              // c7 — deleted_at + 30 days
}
```
Consumes: `UnpublishAllResult` and the take-down loop (WO-142);
`cancelSubscription` and `hostedServingState` (BP-060, WO-133 and WO-130);
`signOut` (BP-061, WO-136); `sendEmail` (BP-016) with
`'account': { occasionsFrom: 'REQ-024, REQ-074, REQ-076, REQ-077, REQ-079', stoppable: false }`;
`dbAdmin()` (BP-002); BP-005's `ERASURE_DAYS = 30`.

## Steps
1. Write `tests/account/lifecycle/delete-account.test.ts` and watch the ordering
   and no-row-deleted cases fail.
2. Write `delete-account.ts` in the fixed order.
3. Add the `delete_account` arm to `confirm.ts`.
4. Write `deletion-mail.test.ts`, including the compose-after-tombstone case.
5. Run the mutation check: replacing the tombstone with a `DELETE` must fail both
   the no-row-deleted case and the compose-after-tombstone case.

## Out of scope
- The RLS condition that makes a tombstoned account unreachable through `db()` —
  **BP-002's**, per ADR-051 point 3. This work order stamps; it does not enforce.
- The 30-day purge itself — WO-144.
- Every unpublish outcome and its routing — WO-142's loop, whose three-arm
  `UnpublishResult` handling and empty-arm pin this WO consumes and does not
  restate (ADR-081).
- Answering 410 — BP-004's edge, reading WO-130's state.
- Whether the unused remainder of a paid period is refunded — refunds are deferred
  by owner ruling (REQ-076, REQ-079 non-goals).
- Every sentence in the deletion mail — BP-019's registry; the owner's words.

## Rollback
Delete `delete-account.ts` and both test files, and revert the one arm added to
`confirm.ts`. Accounts already tombstoned stay tombstoned and their stored
`purge_due_at` stands — the customer was promised that date (decision 4), and a
rollback does not move it.
