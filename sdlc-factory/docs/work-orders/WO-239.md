# WO-239 — The WordPress unpublish — two populations, one stored discriminator, and the arm that is empty today

- Branch: wo/WO-239-wordpress-unpublish
- Estimate: ≤1 day

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to BP-048's `code:` globs
> (`src/lib/publish/destinations/wordpress/**`, `tests/publish/destinations/wordpress/**`),
> and is provisional against a repo with no code: if the implementer finds a
> file already present at one of these paths, they stop and log `failed` naming
> the drift rather than merging into it.

> **Read ADR-081 in full before writing a line of this file, including its
> warning block.** This is the fourth BP-048 work order — the one deliberately
> never cut while BP-048 carried `blocked-by: [REQ-079]`. Half of what it ships

> passing suite. The tests below are what make deleting it fail loudly.

## Goal
Ship the WordPress adapter's `unpublish`: a page ReachKit made live is returned
to draft in the customer's own site by one write of one field, a page it never
made live is named for the customer and not touched, and which of the two
happens is read from `publications.made_live_by_us` and from nothing else.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/wordpress/unpublish.ts` | NEW | `unpublishWordPress(pub: Publication, cfg: DestinationConfig): Promise<UnpublishResult>` — the whole of ADR-081's ruling for this destination, and nothing else. Reads `pub.madeLiveByUs` (the `publications.made_live_by_us` column WO-208 creates, carried on the `Publication` WO-206 declares). **`false` → `{ ok: true, outcome: 'named_for_removal' }` with zero outbound calls**: not the post status, not a tag, not a comment, and not a removal of the marker (ADR-080 decision 5). **`true` → one `POST` through WO-236's client setting that post's status to `draft`, and nothing else** — no other field is read, edited or reordered — then `{ ok: true, outcome: 'returned_to_draft' }`. Idempotent: a post already `draft` returns `returned_to_draft` (setting draft to draft is a no-op); a post the customer has since deleted returns `named_for_removal`, not a failure, because there is nothing left to return and nothing was lost. Any other failure maps through WO-236's `errors.ts` to `{ ok: false, reason }`. **The customer's site is never read to decide the arm** — see the note under Interfaces. |
| `tests/publish/destinations/wordpress/unpublish.test.ts` | NEW | The two arms, the idempotence pair, the deleted-post case, the no-write assertion, and the two mutation tests below. Both arms are exercised against fixture `Publication` rows — the `made_live_by_us = true` fixture is constructed directly, because no production path can produce one (ADR-081). |

`unpublish.ts` is a fifth file inside BP-048's `wordpress/**` glob; BP-048's
module table names four (`adapter.ts`, `client.ts`, `seo.ts`, `errors.ts`) and
places `unpublish` among `adapter.ts`'s members. Splitting it out is a file-plan
choice under rule 1.1: it keeps this work order and WO-237 off a shared file so
both can be worked and reverted independently, and it puts ADR-081's two arms in
a module of their own rather than three levels inside the delivery path, where
"why are there two branches here?" is exactly the question ADR-081 exists to
answer. `adapter.ts` binds `unpublish: unpublishWordPress` (WO-237, amended in
the same pass). Cost of reversing: merge two files. Reported to the architect,
not fixed in BP-048.

## Interfaces

**Consumes**

```ts
// BP-045 · src/lib/publish/types.ts (WO-206) — declared in the leaf
/** ADR-081. Three outcomes, never a boolean: a boolean cannot separate "the
 *  post ReachKit made live is a draft again" from "the post ReachKit never made
 *  live was named and not touched", and those are two different promises to the
 *  customer about their own site. */
export type UnpublishResult =
  | { ok: true;  outcome: 'removed' }             // hosted — REQ-056 c15, 410 at BP-047
  | { ok: true;  outcome: 'returned_to_draft' }   // WordPress, made live by us — REQ-079 c4
  | { ok: true;  outcome: 'named_for_removal' }   // WordPress, never made live — REQ-056 c16
  | { ok: false; reason: FailureReason }

export type FailureReason =
  | 'network' | 'timeout' | 'destination_unavailable' | 'rate_limited'
  | 'credentials_expired' | 'credentials_invalid' | 'dns_not_pointed'
  | 'destination_rejected' | 'no_destination'

// BP-045 · the member this module implements, quoted from `DestinationAdapter`:
  /** Which arm is taken is read from `publications.made_live_by_us`, never from
   *  a re-read of the destination — ADR-081. */
  unpublish(pub: Publication, cfg: DestinationConfig): Promise<UnpublishResult>
```

- `Publication` and `DestinationConfig` — `src/lib/publish/types.ts` (WO-206).
  `Publication` carries the `publications` row WO-208 creates, including
  `made_live_by_us` and `remote_id`.
- The authenticated REST calls and the error mapping —
  `wordpress/client.ts` and `wordpress/errors.ts` (WO-236). Every outbound call
  in this module goes through them and therefore through BP-006's `safeFetch`.
- `WordPressConfig` — declared in `adapter.ts` alongside the adapter (BP-048).
  This module takes `cfg: DestinationConfig` in the signature BP-045 fixes and
  narrows it with `import type { WordPressConfig } from './adapter'`, a
  type-only import erased at compile time — the same posture WO-236 takes, and
  it closes no runtime cycle with `adapter.ts`'s value import of this module.

**Exposes**

```ts
// src/lib/publish/destinations/wordpress/unpublish.ts
export function unpublishWordPress(
  pub: Publication, cfg: DestinationConfig
): Promise<UnpublishResult>
```

**The discriminator is a stored fact, and there are exactly two things that must
never be substituted for it** (ADR-081 decision 2, alternatives 4 and 5 — both
rejected on evidence, both of which read as the obvious implementation):

- **Not `pub.liveUrl != null`.** BP-048 leaves `live_url` null for *every*
  WordPress delivery by design, so this predicate classifies every WordPress
  page as never-live and quietly reduces "unpublish everything" to "touch
  nothing" for the whole population REQ-079 criterion 4 was written about.
- **Not a re-read of the post's status at unpublish time.** A customer who
  published our draft themselves is not a page ReachKit made live, and writing
  into a post the customer chose to publish is the harm REQ-060's non-goals and
  REQ-056's name. The stored fact is about what *we* did; the site's state is
  about what *they* did.

`servesPublicly` is also not the discriminator: it is a property of the
destination, `madeLive`/`made_live_by_us` a fact about what one call did to one
page.

**The was-live arm is empty today.** REQ-060 criterion 1 promises a WordPress
post is never made live by us, and BP-048 has no code path that sets any status
but draft — so `made_live_by_us` is `false` on every WordPress publication this
product can currently create, and every real WordPress unpublish takes
`named_for_removal`. `returned_to_draft` is specified, tested against a fixture,
and unreachable in production until the product gains the ability to publish
into a customer's WordPress live. It is not dead code: it is the branch REQ-079
criterion 4 promises, held open against the day that ability arrives. Deleting
it looks like a cleanup with a passing suite; the two mutation rows in the test
plan are what stop that.

## Steps
1. Read ADR-081 in full, then ADR-080 decision 5. Every simplification this
   module invites is one of the two ADRs' landmines, and none of them makes a
   happy-path test fail.
2. Write `tests/publish/destinations/wordpress/unpublish.test.ts` first, all
   nine rows, and run it: every row must fail on a missing module (constitution
   §8, watch it fail first).
3. Implement the `made_live_by_us = false` arm first, as an early return with
   **no client call at all**. The zero-egress assertion is the test of REQ-056
   criterion 16 and of ADR-081 decision 4; write the arm so the egress seam is
   not merely unused but unreachable — the client is not imported into that
   path.
4. Implement the `made_live_by_us = true` arm as exactly one `POST` setting
   `status: 'draft'` on `pub.remoteId`, through WO-236's client. Send no other
   field. Do not delete the marker, do not touch a tag, do not add a comment
   (ADR-080 decision 5: a cleanup that strips the marker while returning the
   post to draft is the same landmine).
5. Map the deleted-post response (404 on that post id) to
   `named_for_removal`, not to a failure. Map everything else through
   `errors.ts`, whose default arm is non-retryable (BP-048 decision 3).
6. Mutate, and confirm each fails:
   - replace `pub.madeLiveByUs` with `pub.liveUrl != null` — the was-live
     fixture then takes `named_for_removal` and the c4 row fails;
   - delete the `returned_to_draft` branch and let both populations fall
     through to `named_for_removal` — the was-live fixture fails;
   - remove the zero-egress assertion's guard by calling the client on the
     never-live arm — the c16 row fails.

**Discriminates (mutation check, constitution §8).**
- **Deleting the `returned_to_draft` branch** — the change ADR-081's warning
  block is written against — leaves every production-shaped test green, because
  no production path produces a `made_live_by_us = true` row. It fails the
  REQ-079 c4 row and the disagreeing-fixture row, both of which construct that
  row directly. Together with WO-206's type-level exhaustiveness test (deleting
  the arm from `UnpublishResult` stops the type-check), the arm cannot be
  removed silently at either level: WO-206 pins that the arm *exists*, this work
  order pins that it is *taken*, and neither alone is sufficient.
- **Substituting `live_url != null` for `made_live_by_us`** passes every row
  whose two fields agree and fails the two whose fields disagree.
- **Calling the client on the never-live arm** — even a harmless GET — fails the
  c16 row's zero-egress assertion.

## Out of scope
- `publications.made_live_by_us` itself: the column is WO-208's, and it is
  written from `DeliveryResult.madeLive` by `publish()` (WO-213). This module
  only reads it.
- `publications.unpublished_at`, the `published → unpublished` edge, and
  returning the outcome to a caller — BP-045's `unpublish()` (WO-214), which
  passes this module's `UnpublishResult` through unchanged.
- The hosted `removed` arm — WO-228.
- `deliver`, the marker's creation, the SEO write and `health` — WO-236,
  WO-237, WO-238. This module creates no post and writes no marker.
- Orchestrating "unpublish everything" across a site's destinations, and the
  `stillLive` list for a destination that cannot be reached — BP-063.
- Every customer-visible string. This module returns an `UnpublishResult`
  handle; the never-live line is BP-048's copy key
  `publish.wordpress.namedForRemoval` rendered by BP-001, and the was-live line
  has no key named anywhere in the corpus yet (second `rests-on` row). Neither
  is composed here and neither blocks this work.
- Deleting the marker, the publication row, or anything else at either
  destination — ADR-080 decisions 2 and 5.

## Rollback
Delete both files. `adapter.ts` (WO-237) binds `unpublish: unpublishWordPress`
from this module, so reverting this work order leaves `wordpressAdapter` short
of one `DestinationAdapter` member and the type-check fails — which is the
correct behaviour: it is a build failure rather than an adapter that silently
does nothing when a customer asks for their pages back. Revert this only
together with WO-237, or before it lands. Nothing is stored and no migration is
involved; no request is made to any customer's site by either arm's absence.
