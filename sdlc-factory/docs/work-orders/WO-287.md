# WO-287 — The report address's own sentences enter the copy registry — eighteen ruled strings under fixed keys, and the subject slot reaches renderMeasured

- Branch: wo/WO-287-ruled-copy-entries
- Estimate: ≤1 day

## Goal
Make every sentence the report address speaks resolvable from the copy registry: the eighteen strings the owner ruled on 2026-09-04 land under fixed `CopyKey` names with their slots declared and their `fixedBy` recorded, and `renderMeasured` gains the one member the two ruled unmeasured lines need to render at all.

**Risk: normal.** The order moves no money, reads no session, calls back to no third party and publishes to nothing. It touches none of the seams the charter names (`00-project.md`: the SSRF fetcher, the cost seam, Stripe webhook handling, the `sendEmail()` seam, the `llm()` seam). Its criteria are byte-comparison and slot-declaration assertions a plain test discriminates directly — a mis-typed apostrophe fails a byte-for-byte comparison against the ruling file outright rather than surviving it.

**`ui: no`.** No route, no component, no token, no layout: the files are the copy partitions and the `Measured<T>` renderer, all inside `src/lib/presentation/**`. This is WO-041's kind of order, not WO-070's — WO-070 was `ui: yes` because it built the landing screen around its eight strings, not because it entered them. The screen these eighteen sentences appear on is WO-282's, whose v1 preview is already signed.

## Slice (rule 2.6)
One capability, interface to test: the report address's sentences, from their key names through their slot declarations to the renderer that fills them. It is above the floor and it is not half of WO-282 — each states its goal and stop condition without citing the other. This order stops when the eighteen keys resolve and the registry's coverage counts read 17 owner-owed / 53 filled / 70 total; WO-282 stops when every `AddressState` arm renders with exactly one control and one removal address. WO-282 consumes `copy()` and `CopyKey` — an interface BP-019 declares, not this order — and its file plan names no partition file. Neither order can be merged into the other without merging a registry into a route.

WO-041 (the registry itself) and WO-278 (the five seeded keys) are both `status: done` and terminal; neither can be amended, so a scoped amendment was not available and a new order is the only home.

`sdlc-factory/docs/registry/evidence/RULING-copy-2026-09-04.json` — the owner's ruling, byte for byte. Every value in this order's file plan is copied from that file. No value appears anywhere in this work order.

## Where the thirteen live, and why
All thirteen are sentences of one surface — the public report address, `src/app/(public)/scan/[domain]/_address/**`, BP-022's node — and `keys/report.ts` is that surface's partition. `report.ts`'s own header records the precedent this follows: WO-070 put the landing page's eight keys there 'rather than in a thirteenth partition (constitution rule 2.2/BP-020 decision 5's own reasoning, applied the same way WO-249 applied it to `laws.ts`)'. A partition file has to earn itself; a thirteenth would also break the closed-list assertion in `registry.test.ts` for nothing.

The five that already exist keep their homes: `verdict.limiting.*` in `keys/report.ts`, `unmeasured.*` in `keys/laws.ts` beside the law tag that scopes them.

## Slot declarations, and their derivation (rule 1.1)
`CopyMeta.slots` takes `text | date | measured` (`src/lib/presentation/copy/registry.ts`). All four ruled slot names are `text`. Cost of reversing any one: one word in a `slots` map plus the caller's argument type — no customer-visible consequence, because the kind is never rendered; it only decides which function may fill the slot.

| Slot | Keys | Kind | Derivation |
|---|---|---|---|
| `what` | `unmeasured.undeterminable`, `unmeasured.not-attempted`, `notice.incomplete` | `text` | It names *what* was not measured — a driver's name or an `UnmeasuredPart` — never a measurement's value, so `measured` states the wrong thing about it. `measured` is also uninhabitable here, not merely wrong: `copy.ts` refuses any key declaring a measured slot ('use explain() instead'), and `renderMeasured` reaches these two keys through `copy(o.unmeasuredLine)`, so a measured slot would make the unmeasured branch throw for every unmeasured value. `date` is not a date. |
| `address` | `removal.line.on-report`, `removal.line.removed` | `text` | The value substituted is `copy('removal.address')` itself — one key, one address, which is what REQ-002 criterion 3's 'names the address criterion 1 names' requires. Not a measurement and not a date. |
| `domain` | `removal.line.removed` | `text` | The domain segment of the report address — a routing identifier, not a measurement. `measured` is unfillable on this arm besides: `AddressState`'s `{ kind: 'removed' }` carries no `StoredReport` and no `Measured<T>` at all (WO-286), and `explain()` requires a `Measured` with a scan date per slot. |
| `wait` | `notice.refused.network-limit`, `notice.refused.scan-running` | `text` | REQ-003's third `rests-on` row, `disposition: confirmed`: 'A free visitor has no account and therefore no stated timezone, so every time this requirement tells a visitor is an elapsed duration, never a clock time.' `date` is this registry's kind for a clock time — `stopped.work.resumes-on`'s `date` slot and `next-publish.scheduled`'s `at` slot are both instants. An elapsed duration formatted by the refusal's own producer is text. `measured` is out for the same reason as `domain`: the `refused` arm carries a `Refusal`, no `Measured<T>` and no scan date. |

**No `law` tag on any of the thirteen.** `CopyMeta.law`'s four arms are `next-publish`, `stopped-work`, `no-presence-yet` and `unmeasured`, and the conformance suites 'enumerate their own scope from this tag'. The `unmeasured` scope is the pair `renderMeasured`'s `unmeasuredLine` argument takes (`keys/laws.ts` header); `notice.incomplete` is REQ-001 criterion 14's report-level notice and is never passed to `renderMeasured`, so tagging it would widen that suite onto a key it cannot render. This is the posture `report.ts` already records for its eight landing keys.

## Decisions taken under rule 1.1
1. **`notice.measurement-failed` is fixed by REQ-001 c16, not REQ-003 c4.** Both criteria state the same promise from different sides: REQ-003 c4 at the moment a scan ends, REQ-001 c16 at the report address a visitor later opens. The sentence is rendered from the `AddressNotice` arm `measurement_failed`, which `resolveAddress` produces and which WO-286's own test plan traces to REQ-001 c16. One claim, one home (rule 2.4): the address-side criterion holds it and REQ-003 c4 cites it. Cost of reversing: one string in one `fixedBy` field.
2. **`removal.line.on-report` is fixed by REQ-002 c1, not given a criterion of its own.** Criterion 1 requires the address to be *named in writing* on the report; the address key alone is a value with no sentence around it. Both keys therefore carry c1, and the test plan asserts they name the same address. Cost of reversing: one `fixedBy` field.
3. **`rescan` gets two keys, not one with a slot.** `AddressControl` is `{ kind: 'rescan'; because: 'incomplete' | 'age' }` (WO-286), and the owner ruled two distinct labels for it. Two keys keep the choice a total switch over `because` rather than a string built at the call site. Cost of reversing: one key.
