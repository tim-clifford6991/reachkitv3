# WO-251 — `OnPageFacts` and the deterministic on-page parse

- Branch: wo/WO-251-onpage-parse
- Estimate: ≤1 day

## Goal
Turn one fetched HTML document into the counted facts every driver is computed
from — headings, question-shaped headings, direct-answer blocks, evidence
tokens, structured data, Open Graph tags and the document's own access gates —
deterministically, with no fetch, no clock and no JavaScript execution.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW. `src/lib/measure/` is
BP-010's row in `structure.md` ("The measurement engine — deterministic parse of
fetched HTML into four measured quantities …") and BP-010's `code:` globs are
`src/lib/measure/**` and `tests/measure/**`. Neither path is claimed by BP-024,
the only leaf under this component, whose `code:` names five files by name
(`measured.ts`, `partition.ts`, `score.ts`, `bands.ts`, `verdict.ts`) and
`tests/measure/verdict/**` — so `parse.ts` and `tests/measure/domain/**` fall to
the component under `structure.md` rule 2.

**Reuse check (rule 7.2).** `capabilities.md` has no row for HTML parsing and no
work order in the corpus creates a parser: the file-plan rows under
`src/lib/measure/` are WO-052 (`measured.ts`), WO-053 (`partition.ts`), WO-054
(`score.ts`, `bands.ts`) and WO-055 (`verdict.ts`), all of which take numbers
already produced and none of which reads HTML. This work order creates the
capability; it does not duplicate one.

**Status.** Left `status: draft` — written and not self-certified in the same
pass. A later audit sets the status against §3's gate list.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/measure/parse.ts` | **NEW** | The whole public interface below. `visibleText(html)` strips script, style, template and comment nodes and returns the document's rendered text — no JavaScript is executed and no headless browser is used (BP-010 `## Error & edge behavior`: "No JS execution, no clock in the parse, no locale-dependent collation"). `parseOnPage(html)` returns `OnPageFacts` in one pass over the parsed tree: every `h1`–`h6`; the question-shaped subset, by `BUILD.md` §5's own test — "ends `?` or opens with how/what/why/when/where/which/who/can/do/does/is/are" — matched case-insensitively against the ASCII-lowercased heading text and against no other vocabulary; for each question-shaped heading, whether the first block element after it is inside the direct-answer window read from BP-005; the evidence tokens (numerals, dates, outbound citations) and the visible character count they are counted per 1,000 of; the JSON-LD and microdata types present; the Open Graph property set; and the document's own access gates (a `noindex` in a `<meta name="robots">` or equivalent, and whether that directive names every reader or only some). **Counts only — no score, no ratio, no floor and no coefficient appears in this file**: those are WO-252's. Every field is a plain number, boolean or readonly array; no field is `Measured<T>`, because a parse of a document we successfully read cannot be `unmeasured` and the empty denominators read 0, never null (BP-010 `## Error & edge behavior`). Pure: same input, byte-identical output; no `Date`, no `Intl`, no `toLocaleLowerCase`, no `Math.random`. |
| `tests/measure/domain/parse.test.ts` | **NEW** | The suites named in the test plan, over checked-in HTML fixtures held inline in the file. |

## Interfaces

**Consumes:**

> BP-010 decision 2 puts the direct-answer character window in BP-005, and
> `BUILD.md` §5 fixes it verbatim: "`directAnswers` = question headings whose
> first block is 40–320 visible chars ÷ all headings × 100". BP-005's
> `## Public interface` on disk declares no pin carrying it, so WO-006 will not
> have written one. If `SCORING` (or a differently-named pin carrying the same
> two numbers) is absent from `src/lib/config/constants.ts` when this work order
> starts, the implementer **stops and logs `failed — next: BP-005 carries no pin
> for BUILD.md §5's direct-answer character window, which BP-010 decision 2
> assigns to it — reported by the planner 2026-08-31`**. They do **not** write
> `40` or `320` into `src/lib/measure/` (`structure.md` rule 5: "A number that
> appears in two files is wrong"), and they do not add the pin to
> `constants.ts` themselves — that file is BP-005's, and one capability has one
> owner (rule 7.1).

**Exposes** — `OnPageFacts` is *derived here*, not copied: no blueprint declares
it (second `rests-on` row). Every field below traces to a sentence in BP-010's
`## Module / boundary` or in `BUILD.md` §5, quoted in the comment beside it.

```ts
/** The counted facts of one fetched document. Named by BP-010's `measureDomain`
 *  return type and by BP-012's `StoredReport` (`onPage: OnPageFacts // BP-010`);
 *  declared here for the first time. Counts only: nothing in this type is a
 *  score, a ratio, a floor or a band. Empty denominators read 0, never null. */
export interface OnPageFacts {
  url: string
  /** `BUILD.md` §5: "question-shaped headings ÷ all headings". */
  headings: number
  /** §5: "question-shaped = ends `?` or opens with how/what/why/when/where/
   *  which/who/can/do/does/is/are". */
  questionShapedHeadings: number
  /** §5: "question headings whose first block is 40–320 visible chars". The
   *  window is BP-005's pin; this field is the count that passed it. */
  directAnswerHeadings: number
  /** §5's evidence density inputs, counted raw. The saturating log curve over
   *  them is WO-252's, not this file's. */
  numerals: number
  dates: number
  outboundCitations: number
  visibleChars: number
  /** BP-010 `## Module / boundary`: "the parsers (headings, answer blocks,
   *  evidence density, schema, OG)". Types and property names as written in the
   *  document, lowercased; no interpretation. */
  schemaTypes: readonly string[]
  openGraphProperties: readonly string[]
  /** The document's own access gates. REQ-004 c7's case — "a home document the
   *  scan read that tells every reader not to index it" — is
   *  `noindex && noindexAppliesToEveryReader`. What that *means* for the score
   *  is WO-252's; what it means for the blocked-readers count is BP-024's. */
  noindex: boolean
  noindexAppliesToEveryReader: boolean
}

/** The document's rendered text. Exported because BP-010 decision 4's
 *  `readMeasuredText` re-reads `fetches.payload` and must produce the same text
 *  the measurement was taken from — a second extractor would make the
 *  comparison set disagree with the measurement (rule 7.2). WO-253 imports
 *  this one. */
export function visibleText(html: string): string

/** Deterministic and total: any string parses, including an empty one, which
 *  yields every count at 0. Never throws. */
export function parseOnPage(a: { url: string; html: string }): OnPageFacts
```

## Steps
1. Read `src/lib/config/constants.ts` for the direct-answer window. If the pin is
   absent, take the stop condition above — do not improvise one.
2. Write `tests/measure/domain/parse.test.ts` first and run it; every case must
   fail on a missing module before any of `parse.ts` exists (constitution §8,
   "Watch it fail first").
3. Implement `visibleText` first: strip `<script>`, `<style>`, `<template>` and
   comment nodes, then take the text content. No JavaScript is executed and no
   network is touched.
4. Implement `parseOnPage` as one pass producing every field. The question-shape
   test is the twelve openers and the trailing `?` of `BUILD.md` §5 and no other
   token; add none and drop none.
5. Count the direct-answer headings by measuring the *visible* characters of the
   first block element after each question-shaped heading against the pin's two
   bounds inclusive, so the boundary values 40 and 320 both pass.
6. Count evidence tokens and `visibleChars` from the output of `visibleText`, so
   markup can never inflate a numeral or a date.
7. Read the access gates from the document only. `robots.txt` is BP-006's
   `readRobots` and is not fetched, parsed or consulted here.
8. Mutate to prove the suite discriminates: replace the twelve-opener test with
   "ends `?`" alone and confirm the opener fixture fails; replace `visibleText`
   with a raw `innerHTML` and confirm the markup-inflation case fails.

| `BUILD.md` §5: "`directAnswers` = question headings whose first block is 40–320 visible chars ÷ all headings × 100" | `… › the direct-answer window is inclusive at both bounds and read from the pin` — blocks of 39, 40, 320 and 321 visible characters after a question-shaped heading yield 2 of 4 counted; the two bounds are asserted to come from `SCORING`, and a source assertion holds that neither `40` nor `320` appears as a literal in `parse.ts`. |
| `BUILD.md` §5: "`evidenceDensity` = saturating log curve over (numerals + dates + outbound citations per 1k chars)" — **the counts only; the curve is WO-252's** | `… › evidence tokens are counted over rendered text, never over markup` — a fixture whose `<script>` block holds twenty numerals and whose visible text holds three yields `numerals: 3`; `visibleChars` excludes the script. | BP-010 `## Error & edge behavior`: "A home document read successfully that tells every reader not to index it is a measured 0 for Foundations and forces the score to 0 with its band word — it is never a \"—\" (REQ-004 criterion 7)." — **the fact only; the forcing is WO-252's** | `… › a generic noindex and a targeted one are different facts` — a document with `<meta name="robots" content="noindex">` yields `noindex: true, noindexAppliesToEveryReader: true`; one that disallows a single named agent yields `noindex: true, noindexAppliesToEveryReader: false`; one with neither yields both false. Additional tests this work order owns:
- `… › `visibleText` is the one extractor` — a source assertion that no other
  file in this plan re-implements text extraction, and that `visibleText` is
  exported. WO-253's `readMeasuredText` imports it; a second extractor would let
  the generation comparison set disagree with the measurement it came from
  (BP-010 decision 4, rule 7.2).
- `… › the parse never throws` — malformed, truncated, empty and
  non-HTML inputs each return an `OnPageFacts` with zeroed counts rather than
  rejecting; BP-006 already turned every failure into a typed outcome, so a
  throw here would reintroduce the exception path that node removed.
