# WO-237 — The WordPress adapter — a draft, never live, at most one post, and the marker that makes it so

- Branch: wo/WO-237-wordpress-adapter
- Estimate: ≤1 day

## Goal
Ship `wordpressAdapter`: create the page in the customer's own WordPress as a draft, search for our marker before creating so a lost answer never produces a second post, and take down nothing that we did not create.

## Interfaces

**Consumes**

- `DestinationAdapter`, `DeliveryResult`, `RenderedPage`, `UnpublishResult`, `Publication`, `DestinationHealth` — `src/lib/publish/types.ts` (WO-206).
- The REST calls and the error mapping — `wordpress/client.ts` and `wordpress/errors.ts` (WO-236).
- `detectSeoPlugins` and the title/description write — `wordpress/seo.ts` (WO-238).
- A decrypted `DestinationConfig` supplied by BP-058's `withConfig` for the duration of one call (WO-224). This adapter holds nothing.
- `copy()` — BP-019, for the key `publish.wordpress.awaitingYou`. The sentence is the owner's.

**Exposes** — copied exactly from BP-048's `## Public interface`:

```ts
// src/lib/publish/destinations/wordpress/adapter.ts
export const wordpressAdapter: DestinationAdapter   // kind: 'wordpress'

export interface WordPressConfig {          // the shape stored in destinations.config, sealed by BP-058
  baseUrl: string                           // the customer's site root; the REST root is derived, never stored twice
  username: string
  applicationPassword: string               // present only in memory, only inside one call
}

// deliver(): creates the post as a draft, or finds the one we already created
export type WordPressDelivery = DeliveryResult & {
  liveUrl: undefined                        // never set: we never make it live
  madeLive: false                           // ADR-081's discriminator, narrowed to false
                                            // by type: REQ-060 c1 is upheld by there
                                            // being no value this adapter could return
  remoteId: string                          // the WordPress post id
  seoWritten: readonly SeoPlugin[]          // possibly empty — criterion 4's case
  deliveredAt: Date
}
```

**`madeLive: false` is a literal type, not a value this file chooses.** BP-048
narrows it in the declaration above, so REQ-060 criterion 1 ("never made live by
us") holds by construction at every one of this adapter's returns — the same
posture as `liveUrl: undefined`. Widening it to `boolean` is not a
simplification: it is what would let a later edit make a customer's post live and
have every test still pass.

**The marker is the second half of the at-most-once guarantee — ADR-080.** The
unique index on `(draft_id, destination_id)` protects a table in our database; it
cannot see inside a customer's WordPress. The case REQ-056 criterion 5 names
explicitly — "a retry of an attempt whose outcome was never confirmed" — is
precisely the case where we called the destination, it created the post, and we
lost the answer. **Neither the marker nor the publication row may be cleaned up.**
The marker looks like our metadata polluting somebody else's site; it is on our
own post, at creation, and never on a post we did not create. Changing its shape
is a migration of somebody else's site and requires a fallback that finds the old
shape first (ADR-080 decision 5).

**`unpublish` is WO-239's, and it has two arms.** BP-048's
`blocked-by: [REQ-079]` was discharged by **ADR-081** on 2026-08-31: the owner
ruled *scope by liveness*, so REQ-056 criterion 16 and REQ-079 criterion 4 are
each true of their own population and neither narrows the other. A page ReachKit
actually published to the customer's WordPress is returned to draft there
(`returned_to_draft`); a page it created but never made live is named for the
customer and not touched (`named_for_removal`). Which arm is taken is read from
`publications.made_live_by_us`, never from a re-read of the customer's site. The
whole of that behaviour, both arms, is **WO-239** — the fourth BP-048 work order,
never cut until this pass. This file binds the member and implements none of it.

**`servesPublicly: false`** is what leaves `live_url` null, which is what leaves
`verify_due_at` null (WO-213), which is what makes BP-049 exclude this
destination from the 24-hour check by the stated rule — the null address, not the
kind (WO-232).

## Steps
1. Read ADR-080 in full before writing `deliver`. The marker is inert data whose removal makes no test fail except the one this work order writes.
2. Create `adapter.ts` with the block above verbatim, plus `servesPublicly: false`.
3. Implement `deliver`: search for the marker first, return the existing post on a hit, otherwise create with status draft and write the marker at creation.
4. Write the SEO fields by calling WO-238's `seo.ts`. A write that fails while the delivery succeeded is reported as a not-written outcome on `seoWritten`, **never as a failed publish** — the page is in their site, and saying otherwise would be false.
5. Bind `unpublish: unpublishWordPress` from `./unpublish` (WO-239). Write no unpublish logic in this file and no read of `made_live_by_us`.
6. Implement `health` as one authenticated read of the REST index, mapped through `errors.ts`.
7. Write the "a retry after a lost answer creates no second post" test first and watch it fail with the marker search removed — that is the mutation check §8 requires and the reason the test exists.
