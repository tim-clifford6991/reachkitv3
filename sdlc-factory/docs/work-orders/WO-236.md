# WO-236 — The WordPress REST client and the one place a vendor payload stops

- Branch: wo/WO-236-wordpress-client
- Estimate: ≤1 day

## Goal
Ship the authenticated REST calls to a customer's WordPress — every one through BP-006's `safeFetch` — and the error mapping that turns every vendor response into a `FailureReason` and discards the payload.

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/wordpress/client.ts` | NEW | The REST calls, **every one through BP-006's `safeFetch`** with a 2 MB response cap and DNS pinning: the REST index read, the post search, the post create, and the post-meta writes. The REST root is derived from `baseUrl`, never stored twice. Robots checking is **off** for this adapter — these are authenticated API calls to a site the customer connected and gave us a credential for; `robots.txt` governs crawling, not an API the site's own administrator authorised (BP-048's stated rule 1.1 choice). The application password is present only in memory, only inside one call: never logged, never returned by any read path a surface uses, never echoed back to anyone. |
| `src/lib/publish/destinations/wordpress/errors.ts` | NEW | Vendor response → BP-045's `FailureReason`. **The one place a vendor payload stops.** 401/403 → `credentials_expired` (not retryable). 404 on the REST root, or a root that is not a WordPress REST index → `destination_rejected` (not retryable). 429 → `rate_limited` (retryable). 5xx, connection reset, DNS failure, timeout → the retryable members. **A response we cannot classify is not retryable** (BP-048 decision 3): an unrecognised outcome at a destination we do not own must not be hammered three times. The payload is discarded — no vendor string reaches a screen, a mail or an export. |
| `tests/publish/destinations/wordpress/client.test.ts` | NEW | Every call goes through `safeFetch` (a module-graph assertion plus a stubbed seam that throws if bypassed); the 2 MB cap and DNS pinning are in force; a seeded application password appears in **no** log line, error message, thrown stack or returned value anywhere in either file; robots checking is off and a customer `Disallow: /` does not stop a call. |
| `tests/publish/destinations/wordpress/errors.test.ts` | NEW | Each stated status maps to its stated `FailureReason` with its stated retryability; an unrecognised status and an unrecognised body each map to a non-retryable reason; no mapped result carries any part of the vendor payload; a payload containing a credential-shaped string is discarded rather than propagated. |

## Interfaces

**Consumes**

- `safeFetch()` — BP-006, `src/lib/egress/`. SSRF-guarded, DNS-pinned, size-capped.
- `FailureReason` — `src/lib/publish/types.ts` (WO-206), re-exported by BP-045's `attempt/index.ts`.
- `WordPressConfig` — declared in `adapter.ts` (WO-237); this client receives it as a parameter and holds nothing.

**Exposes** — copied exactly from BP-048's `## Public interface`:

```ts
export interface WordPressConfig {          // the shape stored in destinations.config, sealed by BP-058
  baseUrl: string                           // the customer's site root; the REST root is derived, never stored twice
  username: string
  applicationPassword: string               // present only in memory, only inside one call
}
```

`WordPressConfig` is declared by BP-048 alongside the adapter and is created in
`adapter.ts` by WO-237; this work order's client takes it as a parameter.
Credential *storage*, encryption and disconnect-time destruction are **BP-058's**
(WO-224): this adapter receives a decrypted config for the duration of one call
and holds nothing.

**Robots checking off is a deliberate, recorded choice** (BP-048, rule 1.1).
Reversal is one flag, and reversing it would make a customer's own `Disallow: /`
stop their paid publishing.

## Steps
1. Create `wordpress/client.ts` with the four call shapes, every one through `safeFetch`.
2. Derive the REST root from `baseUrl`. Store it nowhere.
3. Create `wordpress/errors.ts` with the mapping exactly as BP-048 states it, and make the default arm **non-retryable**.
4. Discard every vendor payload at the mapping boundary. Log at most a classified reason, never a body.
5. Write the seeded-credential sweep first — seed a recognisable application password, exercise every path including every error path, and assert it appears in no emitted string. Watch it fail against a client that logs the request (constitution §8).
