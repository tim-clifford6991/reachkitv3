# WO-030 — Fonts, the type scale and the numeral rule

- Branch: wo/WO-030-fonts
- Estimate: ≤1 day
- Preview: sdlc-factory/docs/design/previews/WO-029.html
- Signed-off: 2026-09-03

## Goal
Self-host the two fonts and make the numeral rule mechanical: every numeral,
date, URL, search query and code-like string renders in JetBrains Mono with
`tabular-nums`.

## Provenance of this file plan
**This repository holds no `src/`.** Every path is NEW under BP-018's `code:`
glob `src/ui/**`. It shares no file with WO-029 and may run beside it.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/ui/fonts.ts` | NEW | Plus Jakarta Sans (UI) and JetBrains Mono (all numerals/data), loaded from `@fontsource` — self-hosted, so no third-party font request is made from a customer's own domain when BP-004 renders. Exports the two CSS variable names the root layout binds. |
| `src/ui/type.css` | NEW | The scale `BUILD.md` §2.3 fixes: headings Jakarta 700–800, letter-spacing −0.02em, `text-wrap: balance`; body 15px/1.55; uppercase 10.5–11px eyebrows. Plus one utility class, `.num`, that applies JetBrains Mono with `font-variant-numeric: tabular-nums` — the one mechanism the numeral rule is enforced through, so a component cannot half-apply it. |
| `tests/ui/fonts.test.ts` | NEW | The tests below. |

## Interfaces


### 3. The self-hosting test — exactly what it covers, and what it does not

**Covers:** `fonts.ts`'s own `import` specifiers (must start `@fontsource/`, none may match a hosted-CDN pattern or `https?://`), and — for each specifier — the real, on-disk `@fontsource` package file it resolves to via `require.resolve` (not a mock): that file must contain `@font-face` and every `url(...)` inside it must be a relative `./files/...` path, with no `fonts.googleapis.com` / `fonts.gstatic.com` / absolute-URL string anywhere in it. This is a check against the real shipped bytes, not a paraphrase, and it does fail hard when `fonts.ts` itself points at a hosted URL (§1 above).

**Does not cover:** any third-party font request introduced anywhere *except* through `fonts.ts`'s own import list — confirmed by mutation (table, row 6): a hand-written `@font-face` with a `fonts.gstatic.com` `src`, added directly to `type.css`, is invisible to this suite, because the test never parses `type.css` for `@font-face` rules or scans any other file in the tree for a `<link>`/`@import` to a third-party origin. Given this WO's own file plan, that gap is currently inert — `type.css` as shipped declares no `@font-face` of its own and BP-018's `## Module / boundary` names `fonts.ts` as "the one font-loading module" — but it is a real, silent gap in the suite's reach, not a hypothetical one (rule 5.5: state it, don't leave it silent). It would also miss a third-party face introduced via any future file outside `src/ui/fonts.ts` (a root-layout `<link>`, a different module's `@import`) — again out of this WO's own scope, but outside what this test would catch.

Row 2 of the WO's test plan ("hosted-edge render path") is discharged, as the implementer's header comment argues, only because `src/ui/fonts.ts` is currently BP-004's *only* candidate font-loading module — I confirmed no other file under `src/` imports `@fontsource` or references `fontVariables` (`grep -rn` empty), and `src/app` holds only a `.gitkeep` (WO-002's root layout has not landed on this branch). That argument holds today; it is not evidence the promise will still hold once BP-004's hosted-edge renderer exists as a second module — a fact this test cannot see yet either.
