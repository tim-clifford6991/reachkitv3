# WO-238 — Yoast and RankMath — detected, never assumed, and neither present is a success

- Branch: wo/WO-238-wordpress-seo
- Estimate: ≤1 day

## Goal
Ship `detectSeoPlugins()` and the title/description write into whichever of Yoast and RankMath is present — with neither present a successful delivery and a written line, not a failure.

> `code:` globs, and is provisional against a repo with no code: if the

> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/wordpress/seo.ts` | NEW | `SeoPlugin`, `detectSeoPlugins`, and the title/description write. Detection inspects the REST index of the customer's site **once per delivery** — plugins are detected, never assumed. Both present means both written; one present means one written; **neither present is not a failure**. A write to one plugin failing while the delivery succeeded is reported the same way, as a not-written outcome on `seoWritten`, never as a failed publish. | `tests/publish/destinations/wordpress/seo.test.ts` | NEW | Both plugins present → both written and `seoWritten` has two members; one present → one written; neither present → the delivery still succeeds, `seoWritten` is empty and the copy key is carried; a write to one plugin failing leaves the delivery successful and that plugin absent from `seoWritten`; detection makes exactly one REST index read per delivery and never assumes from a version string. |

## Interfaces

**Consumes**

- The REST calls and the error mapping — `wordpress/client.ts` and `wordpress/errors.ts` (WO-236).
- `WordPressConfig` — declared in `adapter.ts` (WO-237); received as a parameter.
- `copy()` — BP-019, for the key `publish.wordpress.noSeoPlugin`. The sentence is the owner's.

**Exposes** — copied exactly from BP-048's `## Public interface`:

```ts
export type SeoPlugin = 'yoast' | 'rankmath'
export function detectSeoPlugins(cfg: WordPressConfig): Promise<readonly SeoPlugin[]>
```

**Neither SEO plugin present is a success, not a degradation** (BP-048 decision
2). `seoWritten: []` sits on a successful `DeliveryResult`; the state machine
reaches `published` in the delivered sense and the line is a copy key on the
page's record. `needs_attention` would be wrong — the page is in their site and
nothing needs the customer. A silent success would also be wrong — criterion 4
requires the telling.

`seoWritten` must survive into the publication record for the line to be rendered
later; BP-048 stores it in the publication row's existing `verify` jsonb sibling
field rather than a new column.

**The writable path is unverified in this corpus** — see `rests-on`. The
implementer discovers it against a real site with each plugin installed and
records what they found; if no writable path exists for one of them,
`seoWritten` simply omits it and criterion 4's line covers the case, which is why
that outcome is not a failure.

## Steps
1. Create `wordpress/seo.ts` with the block above verbatim.
2. Detect by inspecting the REST index once per delivery. Do not assume from a version string and do not cache across deliveries.
3. Write the title and description into each detected plugin's fields. A failure of one write is a not-written outcome, never a failed publish.
4. Return `seoWritten` and name `publish.wordpress.noSeoPlugin` where it is empty. Write no sentence.
5. Discharge the `rests-on` by testing against a real site with each plugin installed and record what was found in the work order log. If no writable path exists for one, omit it from `seoWritten` and say so in the log — do not invent one.
6. Write the "neither plugin present still delivers" test first and watch it fail against an implementation that treats it as an error (constitution §8).
