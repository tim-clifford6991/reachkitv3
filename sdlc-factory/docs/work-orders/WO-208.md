# WO-208 — The publications migration — the unique index that is the at-most-once guarantee

- Branch: wo/WO-208-publications-migration
- Estimate: ≤1 day

## Goal
Add the `publications` columns and the `unique (draft_id, destination_id)` index that make REQ-056 criterion 5 an invariant of the schema rather than a code path, with no `on delete cascade` reaching the table (ADR-080).

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<migration-timestamp>_publications_core.sql` | NEW | The whole delta. `unique (draft_id, destination_id)`; `delivery_state text not null` constrained to `claimed | delivered | failed`; `attempt_no int not null default 0`; `claimed_at timestamptz not null`; `failure_reason text null`; `remote_id text null`; **`made_live_by_us boolean not null default false`** (ADR-081's discriminator — see the note below the interface block); `verify_due_at timestamptz null`; index `(site_id, published_at)`; partial index `(verify_due_at) where verify is null`. Every foreign key into `publications` from `drafts`, `destinations` and `sites` is declared **without** `on delete cascade` (ADR-080 decision 3), with the ADR cited in a SQL comment on each. Timestamp prefix is generated by the migration tool at authoring time; the topic token is `publications`, BP-045's under structure.md rule 3. |
| `tests/publish/attempt/schema.test.ts` | NEW | Schema assertions against a migrated test database: the unique index exists on exactly `(draft_id, destination_id)`; a second insert for the same pair is rejected by the database, not by application code; no constraint into `publications` carries `ON DELETE CASCADE`; `delivery_state` refuses a fourth value; `verify_due_at` accepts null; **`made_live_by_us` exists, is `boolean not null`, defaults to `false`, and accepts `true`** — the last clause matters because no production write path sets it `true` for WordPress today (ADR-081), so a column that silently refused `true` would never be caught by any other test. |

## Interfaces

**Consumes**

- `db()` / `dbAdmin()` and the migration runner — BP-002.
- The baseline `publications` table and its `mode`, `live_url`, `published_at`, `unpublished_at` and `verify jsonb` columns — `BUILD.md` §10, BP-002.

**Exposes** — copied exactly from BP-045's `## Public interface`:

```ts
-- BP-045 "## Data model delta", on the `publications` topic:
--   unique (draft_id, destination_id)          REQ-056 c5
--   delivery_state text not null               claimed | delivered | failed
--   attempt_no int not null default 0          REQ-056 c4's "at most three times"
--   claimed_at timestamptz not null            the moment the attempt was claimed
--   failure_reason text null                   from the FailureReason union; never a vendor payload
--   remote_id text null                        the post id at the destination; never rendered
--   made_live_by_us boolean not null default false
--                                              ADR-081. Written from DeliveryResult.madeLive when the
--                                              outcome is recorded, so it is true only where ReachKit
--                                              itself performed the act that made the page live at that
--                                              destination. It is the whole discriminator between
--                                              REQ-079 c4's population and REQ-056 c16's, and it cannot
--                                              be live_url != null: BP-048 leaves live_url null for every
--                                              WordPress delivery, so that predicate would classify every
--                                              WordPress page as never-live and quietly refuse to take a
--                                              single page down.
--   index (site_id, published_at)              the two ceiling counts
-- BP-049 "## Data model delta", landing in this file because the topic is BP-045's:
--   verify_due_at timestamptz null             published_at + 24h at the moment delivery_state
--                                              becomes delivered; null where live_url is null.
--                                              Due-work index: (verify_due_at) where verify is null
```

**`made_live_by_us` will read as a dead column, and it is not.** Every WordPress
publication this product can currently create leaves it `false` — REQ-060
criterion 1 promises a WordPress post is never made live by us and BP-048 has no
path setting any status but draft — and the hosted adapter sets it `true`, so on
a WordPress-only account the column is a constant. Read ADR-081's warning block
before dropping it, defaulting it away, or replacing it with `live_url is not
null`: the third is the substitution ADR-081 alternative 4 rejects on the
evidence, because `live_url` is null for every WordPress row *by design* and the
predicate would classify every WordPress page as never-live — quietly reducing
"unpublish everything" to "touch nothing" for the whole population REQ-079
criterion 4 was written about. Removing it breaks no test that this migration
does not write.

`verify_due_at` is BP-049's column and lands here because
`supabase/migrations/*_publications*.sql` is BP-045's glob under structure.md
rule 3 — BP-049 says so in its own data-model delta. It is created by this work
order, written by WO-213 and read by WO-232.

## Steps
1. Read ADR-080 in full before writing a line of this file. It is a landmine: every change this work order forbids reads as housekeeping and breaks no test.
2. Write the migration with the columns and indexes above.
3. Add a SQL comment on the unique index and on each foreign key naming ADR-080 and REQ-056 criterion 5, so the next reader of the schema meets the reason before the temptation.
4. Write `tests/publish/attempt/schema.test.ts` against a freshly migrated database and watch the duplicate-insert assertion fail before the unique index exists.
5. Confirm no `on delete cascade` anywhere in the file, and that no other migration in the repository adds one into `publications`.

## Test plan

Each criterion below is inherited verbatim from the requirement named in the
row, reflowed onto one line and otherwise unaltered.

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| **REQ-056 c5** — Given a page and a destination for which a publish has already been attempted, when a publish is attempted again — including a retry of an attempt whose outcome was never confirmed, and an attempt made after the page was unpublished — then at most one post for that page exists at that destination, and a page in `unpublished` gains no post. | `tests/publish/attempt/schema.test.ts` › "a second publication row for the same (draft_id, destination_id) is refused by the database" — the insert is made directly in SQL, bypassing every application path, so the test discriminates the index and not a code branch. |
| _(not a REQ criterion)_ ADR-080 decision 3 — "No foreign key into `publications` carries `on delete cascade`". | `tests/publish/attempt/schema.test.ts` › "no constraint into publications cascades on delete" — reads `pg_constraint` and asserts `confdeltype` is never `c`. Deleting the guard makes this fail, which is the mutation check §8 requires. |
| _(not a REQ criterion)_ ADR-081 decision 2 — the discriminator is a stored fact on the publication row. | `tests/publish/attempt/schema.test.ts` › "made_live_by_us is boolean not null default false and accepts true" — reads `information_schema.columns` for the type, nullability and default, then inserts a row with `true` and reads it back. Dropping the column, or making it a generated expression over `live_url`, fails this test; nothing else in the corpus would notice, which is the whole reason the row is here. |

## Out of scope

- The `destinations` topic — WO-223.
- Writing `made_live_by_us`. This work order creates the column; `publish()` writes it from `DeliveryResult.madeLive` (WO-213) and `unpublish()` reads it (WO-214, WO-239).
- Row-level security policies — BP-002's `*_rls*.sql`.
- Any code that reads or writes these columns.

## Rollback
A down migration dropping the added columns and indexes. Note that dropping the unique index re-arms the duplicate post REQ-056 criterion 5 forbids; a rollback of this file is only safe while no publish path exists, i.e. before WO-212 lands.
